# Workflow

- When the user reports a bug/quirk/visual issue, create a test (screenshot, Playwright, or visual regression) that captures the specific quirk so it doesn't regress — the fix and the test should be done together, not separately. Confidence: 0.70
- When the user approves a multi-phase plan with "keep going", "proceed", or grants broad autonomy, execute through completion without pausing for further confirmation or asking permission for implementation details. Confidence: 0.90
- Do not monkey-patch node_modules dependencies as a debugging/fix strategy; prefer proper solutions like upgrading the package, changing configuration, or restructuring code. Confidence: 0.75
- Avoid extended meta-commentary and self-correction narration between tool calls; just run tools and act. The user gets frustrated when the assistant talks about what it's about to do instead of doing it. Confidence: 0.85
- When working through multi-step verification/testing tasks (e.g. "test each and every component"), store progress to a file so work is resumable and auditable. Confidence: 0.85
- Keep PLAN.md and PROGRESS.md up to date throughout work (not only at completion). They are the source of truth for project state — update phases, gotchas, and next steps as work happens. Confidence: 0.85
- Do not commit changes unless the user explicitly asks; treat commits as a deliberate user action, not an automatic final step of a workflow. Confidence: 0.90
- Maintain LEARNINGS.md at the project root as a running log of non-obvious technical gotchas (build quirks, library bugs, parser pitfalls, spec compliance notes). Update it whenever new discoveries are made — it should grow over time, not be written once. Confidence: 0.85
- When killing dev servers, NEVER use broad patterns like `pkill -f "node"` or `pkill -f "node.*dev"` — this kills unrelated node processes (and can kill the killing shell itself). Use specific patterns (e.g. `pkill -f "vite"`, `lsof -i :PORT -t | xargs kill`) and prefer killing by port. Confidence: 0.95
- Before debugging against a localhost port, verify which port the dev server is actually on (check the dev log for "Local: http://localhost:XXXX/") — don't assume the first preferred port is in use. Stale servers on old ports produce misleading probe results. Confidence: 0.85
- When starting a dev server, capture and remember the PID (e.g. `echo $!` after `nohup ... &`) so it can be cleanly killed later — don't rely on `pkill` patterns that may match unrelated processes. Confidence: 0.85
- Dev servers started from this session are child processes of the CommandCode node session; killing them can terminate the session itself. Always start dev servers detached using `nohup ... > /tmp/devserver.log 2>&1 & disown` or `setsid ... < /dev/null &`, then kill them later via the saved PID or port. Confidence: 0.95
- Never kill the assistant's own CommandCode process under any circumstance — avoid any action (broad `pkill -f node`, killing parent shells, signals that propagate up) that could terminate this session. Confidence: 0.95
- Prefer splitting large test suites into multiple separate test files run consecutively, rather than a single combined file with all test cases. Run each file in turn rather than packing all tests into one file. Confidence: 0.70
- When the user says "remember" or "save to AGENTS.md", persist important project rules/preferences/gotchas to AGENTS.md at the project root as durable, explicit instructions — this is the user's preferred long-term memory file (alongside the taste system). Confidence: 0.85
- The CommandCode (cmd) session runs on Node.js v22; keep this in mind for process/signal/port-handling decisions (e.g. POSIX signals, child process detachment, Node-specific APIs). Confidence: 0.70
- The CommandCode session appears in `ps` output as a `node` process (running the cmd binary), not under the name "cmd" — when identifying or inspecting this session's process, match on `node` with the cmd script path, never look for a process literally named "cmd". Confidence: 0.80
- Configure Playwright so rendered components produce text/structured output describing exactly what they look like, allowing the assistant to reason about visual state without needing vision/multimodal PNG analysis — preferred over vision-based screenshot inspection. Apply this diagnostic approach to ALL components, not just a subset. Confidence: 0.85
- When generating test coverage across prop combinations, test every documented prop as its own variant — do not curate a subset of 3-6 "interesting" props. The user wants exhaustive visual coverage, not a hand-picked selection. Confidence: 0.90
- When encountering odd/unexpected behavior in the quasar-dev playground, restart the dev server as the first troubleshooting step before investigating further. Confidence: 0.65
- Test component combinations (e.g., QBtn in QSticky, QTooltip on QBtn, QAvatar inside QChip) as documented in the Quasar docs — not just isolated single-component variants. Composite/combination tests need their own dedicated preview pages in a separate section of the playground (not just inline test fixtures). Exhaustively catalog every composite pattern from every Quasar doc page — do not stop at a curated subset of 7. Confidence: 0.85
- Composite/combination tests must be style-specific (parameterized across MD2/MD3), not hardcoded to a single style — same as component variant tests. Confidence: 0.65
- After completing a test coverage sweep (visual regression, Playwright tests), create a summary/overview file documenting exactly what was tested — components covered, variants, and any gaps. This gives the user a quick reference of test completeness without digging through test files. Confidence: 0.70
- When systematically scanning/analyzing a large codebase (e.g., checking every Quasar docs example for patterns), write a reusable Node.js script instead of chaining ad-hoc shell one-liners. The script should be saved to disk for later re-use, not thrown away after one run. Confidence: 0.70
- When setting up a new development tool for the project (e.g., sigmap), write self-referencing usage instructions to AGENTS.md so future assistant sessions know how to invoke and configure the tool. The assistant should be able to pick up where it left off without re-discovering the tool. Confidence: 0.75
- Use sigmap (`sigmap ask`, `sigmap --query`) to find files and understand codebase structure instead of scanning with read_directory/glob. Scanning tools push everything into context unnecessarily; sigmap provides targeted, indexed results. Confidence: 0.85
